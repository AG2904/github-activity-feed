# The system ships as two images, and the images pin the patch

The relay and the CLI are two containers built from one `Dockerfile` with two targets, orchestrated by `docker-compose.yml`. The relay keeps its toolchain in a build stage and runs as the unprivileged `node` user; the CLI is a `CGO_ENABLED=0` static binary in a minimal runtime as uid 10001. The CLI's image carries the same binary the release builds — `./cmd/feed` with `-trimpath` and the version stamped through `-ldflags` — so the container is a second way to run the client, not a second client.

The relay needed a stage boundary for a reason that is not tidiness: `better-sqlite3` is a native addon. Either the image trusts a prebuilt binary for the exact platform and ABI, or the build stage installs `python3`, `make` and `g++` and compiles it. Trusting the prebuild means a base-image bump can break the build in a way that says nothing about the code; installing the toolchain costs one build stage that never reaches the runtime. The stage boundary is what lets the runtime be `node:slim` with `NODE_ENV=production` and pruned devDependencies.

The CLI's boundary is the opposite argument. It has no dependencies at all ([ADR-0008](0008-stdlib-only-and-flag-over-cobra.md)), and the Go module is nested at `client/` ([ADR-0009](0009-go-module-nested-in-the-monorepo.md)), so the image exists to prove that a build with no toolchain on the host produces the same bytes as the one that does.

## Considered Options

- **Floating majors (`node:24`, `golang:latest`, `alpine:latest`)** — rejected. A floating tag turns every rebuild into a runtime change nobody reviewed, and the two failure modes are both silent at build time. A `node_modules` compiled against one Node ABI refuses to load its native binding under another, and a Go patch release is a standard-library fix the binary has already absorbed; in both cases the symptom appears when the container runs, not when it builds. The pinned tags are `24.22.1`, `1.27.3` and `3.24.3`, read from `nodejs.org/dist`, `go.dev/dl` and Docker Hub on 26 October 2026. `24.22.1` is an LTS *Krypton* security release; `26.12.1` was rejected even though it is patched, because it is still Current and the relay's CI and documentation speak of Node 24.
- **One image running both halves** — rejected. It would put the Go toolchain and the Node toolchain in the same build, then ship a process supervisor into production to run two processes the project has never needed to co-locate. The two halves of this system are joined by a wire contract over the network, which is exactly what a container boundary expresses.
- **`scratch` instead of an alpine runtime for the CLI** — considered and left for later. It saves a few megabytes and removes the package manager from the runtime, but the binary can talk to an `https://` relay and a static binary carries no trust store, so the CA bundle has to be copied from somewhere. Alpine's `ca-certificates` at `3.24.3` gets that from the distribution's own package rather than from a path inside a builder stage. The security gain was judged smaller than the maintenance oddity of hand-managing a certificate bundle.
- **Publish the relay port on the host's default interface** — rejected. Docker's default publishes on `0.0.0.0`, and `/history` and `/stream` are unauthenticated by design ([ADR-0001](0001-sse-for-realtime-channel.md)). The webhook arrives through a tunnel, not through an open port, so the bind is `127.0.0.1` and reaching the relay from another machine requires saying so explicitly.
- **Run the CLI as a compose service** — rejected. A `watch` is a foreground process attached to a terminal; as a background service it has nowhere to paint. `feed` sits behind the `tools` profile so `docker compose up` starts the relay alone and `docker compose run --rm feed …` borrows the network for one command.
- **Publish the images to a registry from CI** — deferred, not rejected. This ADR leaves images as local build output; `.github/workflows/ci.yml` builds and smoke-tests both, and says nothing about where they are stored. A registry, tags and a signing story are their own decision, and the release workflow ([`release.yml`](../../.github/workflows/release.yml)) is where they would land.

## Consequences

The SQLite file is the system's state, so it moves out of the working directory and onto a named volume at `/data/relay.db`; recreating or upgrading a container leaves the history intact, and `docker compose down -v` is the only destructive command. The published port is loopback-only, and that is load-bearing rather than cautious: the relay's own ADR-0001 makes reads public, so the container boundary must not widen them.

The version numbers live in three `ARG` lines at the top of the `Dockerfile` and nowhere else. Bumping one is a one-line change plus a rebuild — and there is **no automation watching those tags**. Dependabot-style updates were not part of this decision, so a pinned patch goes stale silently from the day it is written. That is the debt this ADR buys with its determinism, and the day it matters the fix is a scheduled job, not a policy change.

The CI `docker` job is the only thing that builds these images. Docker was not installed on the machine where they were written, so the files were authored against the code — `dist/main.js`, `DATABASE_PATH`, `go build ./cmd/feed` — and verified only as far as Docker Hub tag existence, official release indexes, an OSV query over the production dependency tree, and a YAML parse. The job builds both targets and smoke-tests each: `feed --version`, and a `GET /history` against a relay started with a throwaway secret. A Dockerfile that is never built is a hypothesis, and this is where the hypothesis is tested.

The compose file is not a deployment. It terminates no TLS, authenticates no reader, and runs one relay, because SQLite and the in-process SSE broadcast are what they are (ADR-0001). Anyone who wants it reachable and durable beyond a laptop needs the pieces ADR-0001 already lists as out of scope — and a database that is not a file.
